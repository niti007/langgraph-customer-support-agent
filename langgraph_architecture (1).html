Why Pydantic models?
🔒
Guaranteed structured output
LLMs return free-text. llm.with_structured_output(Model) forces the model to emit JSON matching the schema — no string parsing, no regex.
✅
Runtime validation
Pydantic validates every field at parse time. If the LLM hallucinates an invalid priority value, the call raises immediately instead of silently corrupting state.
📐
Typed routing logic
Downstream nodes read result.needs_escalation (bool) or result.priority (Literal) — no dict key errors, full IDE autocomplete.
🧠
Acts as a prompt
Field names and Field(description=...) docstrings are injected into the system prompt automatically. The schema is the instruction.
TicketClassification
Used in classify_ticket via llm.with_structured_output(TicketClassification)
category Literal[5] billing·tech·order…
intent Literal[9] refund_request…
priority Literal[4] low·medium·high·urgent
sentiment Literal[4] positive·neutral…
confidence float 0.0 → 1.0
rationale str short explanation
Why Literal types? Restricts the LLM to exactly the allowed values. A free string field would let the model return "Billing" vs "billing" vs "BILLING" — breaking routing.

Why TypedDict not Pydantic? LangGraph requires the state to be a plain dict subclass so it can merge partial updates from each node. Pydantic BaseModel is used only for LLM I/O where validation is needed.
Why this architecture?
🔁
Stateful graph (not a chain)
A LangChain chain is stateless — it can't pause mid-run. LangGraph's StateGraph checkpoints after every node so the process can suspend for human input and resume later, even in a new Python process.
🪢
Two-gate safety model
Gate 1 reviews the classification before any LLM drafting happens — cheap to catch mistakes early. Gate 2 reviews the draft response before it reaches the customer — last line of defence.
↔️
Conditional routing, not if/else
add_conditional_edges maps routing functions to nodes declaratively. Changing who gets escalated means editing the router, not the node logic — concerns stay separated.
💾
SQLite = free persistence
Every state snapshot is keyed by thread_id. A new customer session gets a new thread. You can replay, audit, or resume any ticket by thread ID — no extra infrastructure needed.
ResolutionDecision
Used in draft_resolution via llm.with_structured_output(ResolutionDecision)
draft_response str customer-facing text
needs_escalation bool routes final gate
escalation_reason str shown to specialist
confidence float triggers gate if <0.80
Why bool for escalation? A typed boolean drives a Python conditional directly. A free-text "yes/maybe/no" string would require fuzzy matching and could silently mis-route tickets.

Knowledge retrieval (RAG)
simple_retrieve(query, category, top_k=3) scores each of 6 KB articles:
+3 ptscategory match
+N ptsword overlap with title+content
top-3injected into LLM prompt
Why not vector search? This lab uses keyword overlap intentionally — simpler to understand and debug. The same pipeline works with any retriever (FAISS, pgvector) by swapping simple_retrieve.

📦 Data flow through the graph

1
Input — customer_id + customer_message enter as the initial state dict.
2
classify_ticket writes 6 new keys to state: category, intent, priority, sentiment, confidence, initial_route.
3
approval_gate either auto-writes approval_decision = "approved" or suspends — the state is checkpointed to SQLite at this exact point.
4
retrieve_knowledge writes retrieved_docs: List[Dict] — a list of matching KB articles passed forward to the LLM.
5
draft_resolution writes draft_response, needs_escalation, escalation_reason, resolution_confidence.
6
final_review_gate either auto-approves or suspends a second time. Human can overwrite final_response directly.
7
resolve_case or escalate_case writes final status and final_response — the only values the caller actually reads.

🏗 Key design decisions explained

🪪
Separate classify from resolve. Classification is cheap (one LLM call, tiny output). Resolution is expensive (retrieval + long prompt). Splitting them means Gate 1 can reject bad classifications before spending tokens on a draft.
🛑
Two gates, not one. A single gate forces a choice: review classification (early, cheap) or review draft (late, safe). Two gates give both. Gate 1 catches routing errors; Gate 2 catches bad responses.
🔑
thread_id per customer session. Means a customer calling back can have their previous context restored. Multiple concurrent customers run in isolated threads — no state bleed.
📊
Confidence thresholds (0.70 / 0.80). These gate thresholds let you tune automation vs oversight — lower them for more human review, raise them for higher throughput. They're the key operational knob.
🧩
Retrieval before drafting. The KB docs are injected into the LLM prompt so the model is grounded in policy. Without this, GPT-4o-mini would hallucinate refund timelines or password reset steps.

🚀 How it runs & how to extend

▶️
Run: graph.invoke(ticket_input, config) — blocks until the first interrupt or END.
⏸️
Resume: graph.invoke(Command(resume={...}), config) — restores from SQLite checkpoint and continues from the paused node.
🔍
Inspect: graph.get_state(config) — returns the full state dict at any point, including pending interrupts.
🔄
Swap the retriever. Replace simple_retrieve with a vector store. The node signature stays identical — only the retrieval implementation changes.
➕
Add a node. builder.add_node("new_step", fn) + add_edge(). The state dict is extended with new keys — existing nodes are unaffected.
📬
Production path. Replace SqliteSaver with PostgresSaver (same API), deploy behind a webhook that calls graph.invoke on each human review action.
